# 要件定義書

## 1. サービス概要

### パルスサーベイとは

- 「脈拍調査」の直訳通り、短い質問（3〜5問程度）を定期的に繰り返すことで、チームや組織の「今の状態」をリアルタイムで把握する仕組み。

### 目的

- 従業員の満足度およびエンゲージメントを定量的・正確に把握し、組織運営の健全化を図る
- 従業員の変化（離職予兆・不満）をリアルタイムに検知し、問題が深刻化する前に改善サイクルを回す
- データに基づいた人事施策のアップデートを定量的に実行する
- 15名という小規模組織ゆえの「特定されるおそれ」をシステム構造で排除し、全従業員が本音を届けられるインフラを構築する

## 2. プロジェクト計画

### フェーズ1：MVPリリース

- **目標時期**: 4月中（遅くとも5月中）
- **主要機能**: アンケート回答機能、全社スコアの自動集計
- **達成目標**: 毎週（または隔週）答えるという習慣の定着と、組織のベースライン（基準値）の把握

**MVPスコープ**

- 従業員がサーベイに回答できること
- 従業員がGoogle Authでログインできること
- 1人1回の回答制御ができること
- 管理者が回答済み / 未回答を確認できること
- 管理者が未回答者へリマインドできること
- 全社平均スコア、カテゴリ別スコア、回収率を確認できること
- 定量回答の匿名性が担保され、個人の回答内容を特定できないこと

**MVP非スコープ**

- Slack連携の自動化
- 時系列ダッシュボードの高度な可視化
- 質問順のランダム化
- 改善アクションログの蓄積と分析
- 自由記述を使った高度な分析やインサイト抽出

### フェーズ2：分析・連携機能の追加

- **主要機能**: Slack連携、時系列スコアの可視化ダッシュボード、質問順番のランダム化
- **拡張機能**: 改善アクションログ（施策とスコア変化の紐付け）、目安箱

## 3. システム要件

### ① ユースケース

- 従業員が定期的にサーベイへ回答する
- 管理者が未回答者を確認し、Slackなどで回答を促す
- 管理者が全社スコアとカテゴリ別スコアの推移を確認する
- 管理者が自由記述を確認し、必要に応じて改善アクションや個別フォローにつなげる
- 管理者が実施した改善内容を組織に共有し、次回以降の参加意欲につなげる

### ② 機能要件

| 機能               | 内容                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| 管理者機能         | 従業員の登録・管理、未回答者へのリマインド通知（誰が答えたかは判別するが、回答内容は紐付けない） |
| 回答機能           | 二重回答を防止                                                                                   |
| 分析ダッシュボード | 全社平均スコアおよびカテゴリー別スコアの推移、回収率の表示                                       |
| 目安箱             | 自由記述による要望記入欄。記名の有無を選択可能                                                   |

### ③ データ設計（匿名性の担保）

- 定量スコアは `score_answers` テーブルに保存し、ここには `user_id` / `submission_id` を一切持たない。
- `submissions`（誰がどのサーベイに回答したか）と `score_answers`（どの設問にいくつスコアがついたか）はDB上で切り離されており、管理者であっても個人のスコア回答を特定できない。
- 自由記述については、`text_answers.submission_id` を通じて「誰のコメントか」を紐づけ可能とし（目安箱・個別フォロー用途）、定量スコア部分の匿名性とは役割を分ける。

### ④ 非機能要件

**セキュリティ**

- 管理者であっても個人の回答を特定できない制約。DB上での物理的分離
- 回答者数が極端に少ない場合、個人の特定を避けるためグラフや詳細数値を表示しないガードレールを設ける

**パフォーマンス**

- Slack APIのレート制限に配慮した設計

### ⑤ 受け入れ条件

- 従業員は対象期間内に1サーベイにつき1回のみ回答できること
- 管理者は誰が回答済みかを確認できるが、個人の定量回答内容は閲覧できないこと
- 全社平均スコア、カテゴリ別スコア、回収率が管理画面で確認できること
- 回答者数が閾値未満の場合は、個人特定を避けるため詳細な集計結果を表示しないこと
- 自由記述は記名・匿名を選択でき、記名時のみ個別フォロー可能であること
- 未回答者へのリマインドが運用可能であり、二重送信や過剰通知を避けられること
- 改善アクションを記録または共有でき、少なくとも「答えて終わり」にならない運用導線があること

## 4. 運用要件

### ① 分析・通知・運用ルール

- 分析は個人単位ではなく、全社またはカテゴリ単位で行う
- 管理者はスコアの増減だけで判断せず、自由記述および過去施策と合わせて解釈する
- 通知は週次または隔週の定例運用とし、未回答者へのリマインドは回答期限前後の必要最小限に留める
- 従業員への共有はスコアそのものではなく、「何を把握し、何を改善するか」を中心に行う
- 改善アクションは実施有無が追跡できる状態にし、次回以降のサーベイ結果と合わせて振り返る
- サーベイ運用の責任者を明確にし、配信、確認、共有、改善までの担当を曖昧にしない

### ② 設問設計

回答のマンネリ化と適当な回答を防止するため、以下の構成で運用する。

定量回答（7問） + 自由記述（1問）の構成をとる

#### 定量回答：

- 4つのカテゴリに沿った質問構成（①基本的なニーズ、②個人の貢献、③チームワーク、④成長）を取る。
- 回答の負担を最小限に抑えつつ、表面的な実態調査にとどまらないよう全7問とする。
- 質問内容の変化によるスコアの揺れを防ぐため、質問は変更せず毎回固定する。
- ただし、慣れによる機械的クリックを防ぐため、質問順をランダムに入れ替える。

#### 自由記述（目安箱）:

- この設問は、定量回答の後に置く。
- 内容は、業務の壁や改善要望、上司へのSOSなどを想定。
- 「特になし」でも回答可とし、サーベイ全体への心理的負担を下げる。

## 5. 形骸化防止策

| アラート         | 条件                                     | 対応                                                                           |
| ---------------- | ---------------------------------------- | ------------------------------------------------------------------------------ |
| 応答率アラート   | 全体の応答率が3週連続で50%を下回った場合 | 仕組み自体を再検討する                                                         |
| 改善停止アラート | アクションログが1ヶ月間更新されない場合  | 管理者はサーベイ配信を一時停止し、運用フローを修正する                         |
| メタアンケート   | 数ヶ月に1回                              | 「このサーベイはあなたに役立っていますか？」を追加し、仕組みの有効性を測定する |

## 6. 懸念事項

以下のような懸念点がある。

- 回答をしない
- 回答が歪む（信頼性が低い）
- 分析結果の活用をしない
- 分析結果の活用ができない（インサイトがない）

## 7. 成功指標

- サーベイ回答率が継続的に一定水準を維持していること
- 回答率の大幅な低下や自由記述の形骸化が起きていないこと
- 管理者が定期的に結果を確認し、改善アクションを実行していること
- 実施した改善内容が従業員に共有され、「答えても意味がある」という認識につながっていること
- 時系列でスコアや自由記述の変化を追え、組織状態の把握に役立っていること
