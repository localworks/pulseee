# 要件定義書

## 1. サービス概要

### パルスサーベイとは

- 「脈拍調査」の直訳通り、短い質問（最初のリリースでは定量7問を標準とする）を定期的に繰り返すことで、チームや組織の「今の状態」をリアルタイムで把握する仕組み。

### 目的

- 従業員の満足度およびエンゲージメントを定量的・正確に把握し、組織運営の健全化を図る
- 従業員の変化（離職予兆・不満）をリアルタイムに検知し、問題が深刻化する前に改善サイクルを回す
- データに基づいた人事施策のアップデートを定量的に実行する
- 15名という小規模組織ゆえの「特定されるおそれ」をシステム構造で排除し、全従業員が本音を届けられるインフラを構築する

## 2. プロジェクト計画

### フェーズ1：MVPリリース

- 主要機能: Google認証、定量サーベイ回答機能、回答率を後から集計できるデータ保存
- 達成目標: サーベイ対象者が安全に定量回答でき、匿名性を壊さず回答状況と回答スコアを蓄積できること

#### MVPスコープ

- 事前登録ユーザーがGoogle認証でログインできること
- サーベイ対象者が、有効かつ未回答のサーベイに回答できること
- 1人1サーベイにつき1回の回答制御ができること
- サーベイを有効化した時点のサーベイ対象者を回答率の分母として固定できること
- システム管理者がRailsAdminでユーザー、標準設問、サーベイを管理できること
- 定量回答の匿名性が担保され、個人の回答内容を特定できないこと

#### MVP非スコープ

- 全社平均スコア、カテゴリ別スコア、回答率の専用表示画面
- 未回答者へのリマインド通知機能
- Slack連携の自動化
- 時系列ダッシュボードの高度な可視化
- 質問順のランダム化
- 改善アクションログの蓄積と分析
- 自由記述（目安箱）と、その分析やインサイト抽出

### フェーズ2：分析・連携機能の追加

- 候補機能:
  - 全社平均スコア、カテゴリ別スコア、回答率の表示
  - 未回答者へのリマインド通知
  - Slack連携
  - 時系列スコアの可視化ダッシュボード
  - 質問順番のランダム化
  - 改善アクションログ（施策とスコア変化の紐付け）
  - 自由記述（目安箱）

## 3. システム要件

### ① ユースケース

- 事前登録ユーザーがGoogle認証でログインする
- サーベイ対象者が有効で未回答のサーベイを表示し、定量回答を送信する
- システム管理者がRailsAdminでユーザー、標準設問、サーベイを設定する
- システムがサーベイ有効化時点の回答対象を固定し、回答率を後から集計できる状態を保つ
- 後続フェーズでは、回答率や集計結果の閲覧、通知、改善運用を追加する

### ② 機能要件

| 機能 | 最初のリリースでの内容 |
| --- | --- |
| 認証 | Google認証に成功し、事前登録済みのユーザーだけがログインできる |
| 管理機能 | システム管理者がRailsAdminでユーザー、標準設問、サーベイを設定できる |
| 回答機能 | サーベイ対象者が有効で未回答のサーベイに定量回答でき、二重回答を防止する |
| 回答対象固定 | サーベイを有効化した時点のサーベイ対象者について、`survey_assignments` を作成する |
| 回答率集計用データ | `survey_assignments` から後で分母と回答済み件数を集計できる |
| 専用集計画面・通知・自由記述 | 最初のリリースでは実装しない |

### ③ データ設計（匿名性の担保）

- 定量スコアは `score_answers` テーブルに保存し、ここには `user_id` / `survey_assignment_id` を一切持たない。
- 定量スコアは回答時刻からの推測も避けるため、`score_answers` に `created_at` / `updated_at` も持たない。
- 同一回答送信内の定量スコアは、回答時に生成する一意な `submit_token` で束ねる。ただし `submit_token` は回答者や回答依頼・回答状態を表すテーブルには保存せず、回答者を特定できないようにする。
- 回答依頼・回答状態を表すテーブル（誰がどのサーベイに回答すべきか）と `score_answers`（どの設問にいくつスコアがついたか）はDB上で切り離されており、システム管理者であっても個人のスコア回答を特定できない。
- 自由記述とその保存方法は最初のリリースの対象外とし、追加時に匿名性と個別フォローの方針を改めて定義する。

### ④ 非機能要件

#### セキュリティ

- システム管理者であっても個人の回答を特定できない制約。DB上での物理的分離
- 集計結果を表示する後続フェーズでは、回答者数が極端に少ない場合に詳細数値を表示しないガードレールを設ける

#### パフォーマンス

- Slack連携を追加する後続フェーズでは、Slack APIのレート制限に配慮した設計にする

### ⑤ 受け入れ条件

- 回答制御:
  - 事前登録ユーザーだけがGoogle認証でログインできること
  - サーベイ対象者は対象期間内に1サーベイにつき1回のみ回答できること
  - 期限切れ、回答済み、対象外のサーベイには回答できないこと
- 回答対象と回答率集計用データ:
  - サーベイが回答可能になった時点の回答対象者が固定され、後から回答率の分母として確認できること
  - サーベイが回答可能になった後に回答対象者となったユーザーは、その既存サーベイの回答率分母に追加されないこと
  - サーベイが回答可能になった後に回答対象者ではなくなったユーザーも、その既存サーベイの回答率分母から除外されないこと
  - 回答率の履歴を壊さないため、回答対象者や回答履歴を持つユーザーは削除せず、次回以降の対象外として扱えること
- 定量回答の匿名性:
  - システム管理者であっても、個人の定量回答内容を特定できないこと
  - `score_answers` にユーザーやサーベイ割当へ紐づく情報、回答時刻を保存しないこと
- 初期運用:
  - システム管理者がRailsAdminで初期運用に必要なマスタとサーベイを管理できること

## 4. 運用要件

### ① 将来の分析・通知・運用ルール

- 以下は集計表示や通知を追加する後続フェーズで適用する。
- 分析は個人単位ではなく、全社またはカテゴリ単位で行う
- 運用責任者はスコアの増減だけで判断せず、自由記述および過去施策と合わせて解釈する
- 通知は週次または隔週の定例運用とし、未回答者へのリマインドは回答期限前後の必要最小限に留める
- 従業員への共有はスコアそのものではなく、「何を把握し、何を改善するか」を中心に行う
- 改善アクションは実施有無が追跡できる状態にし、次回以降のサーベイ結果と合わせて振り返る
- サーベイ運用の責任者を明確にし、配信、確認、共有、改善までの担当を曖昧にしない

### ② 設問設計

- 最初のリリースでは、定量回答のみを扱う。

#### 定量回答

- 回答の負担を最小限に抑えつつ、表面的な実態調査にとどまらないよう全7問とする。
- 各サーベイの設問文と並び順は、サーベイ作成時に標準設問からコピーして保持する。
- 最初のリリースでは、質問順をランダムに入れ替えず、保持した並び順で表示する。

#### 自由記述（目安箱）

- 自由記述は後続フェーズの候補とし、最初のリリースでは回答対象に含めない。

## 5. 形骸化防止策

以下は回答率の表示や改善運用を追加した後に適用する候補とする。

| アラート         | 条件                                     | 対応                                                                           |
| ---------------- | ---------------------------------------- | ------------------------------------------------------------------------------ |
| 応答率アラート   | 全体の応答率が3週連続で50%を下回った場合 | 仕組み自体を再検討する                                                         |
| 改善停止アラート | アクションログが1ヶ月間更新されない場合  | 運用責任者はサーベイ配信を一時停止し、運用フローを修正する                     |
| メタアンケート   | 数ヶ月に1回                              | 「このサーベイはあなたに役立っていますか？」を追加し、仕組みの有効性を測定する |

## 6. 懸念事項

- 以下のような懸念点がある。
  - 回答をしない
  - 回答が歪む（信頼性が低い）
  - 分析結果の活用をしない
  - 分析結果の活用ができない（インサイトがない）

## 7. 成功指標

- サーベイ回答率が継続的に一定水準を維持していること
- 定量回答を匿名性を守った状態で蓄積できていること
- 後続フェーズで集計・改善機能を追加した後は、結果確認と改善アクションにつながっていること
